脑暴 · 网络新闻访问问题

让 popup 里的新闻链接「点开就能读」

角色：中国大陆用户。现象：popup 新闻列表正常，但点开部分境外科技媒体原文（如 TechCrunch）无法连接。 约束：只保证「从我们的 popup 打开」的链接可读；同一 URL 用户自己直接打开通不通，与我们无关。 资源：一台日本服务器（用户与内容源双向可达）、可熟练操作阿里云/腾讯云/Cloudflare。目标：成本尽可能低，最好免费，充分利用现成资源。

一、需求本质是什么（先想透，再动手）

本质 1：这不是「全局网络问题」，而是「应用层内容可达性缺口」

数据链路分两段：聚合端（GitHub Actions / 日本）→ 内容源 可达；阅读端（大陆用户）→ 部分境外源 不可达。 缺口只发生在第二段的「点开原文」这一刻。所以正确答案不是任何系统级方案，而是： 给一个封闭的、我们自己生成的 URL 集合，做一个「应用层内容中继」——用户点开时，让内容经由一条双方都能走的路送达。

本质 2：范围自我限定 = 成本可以压到接近零

「只保证 popup 里打开的链接」是一个极其有利的约束：待保障的 URL 集合是封闭的、已知的、每天可枚举的（就是 latest-24h.json 里那 ~1000 条）。这意味着——

  • 可以做 per-URL 改写/包装（点击时把链接换成中继地址），不需要任何常驻代理；
  • 可以做 允许列表（中继只服务出现在数据集里的 URL），天然防止中继被滥用成公开代理；
  • 甚至可以 提前把内容取回来（构建期快照），点击时完全不再依赖境外源。

本质 3：内容性质决定技术选型——「文字报道」用阅读器模式，不用全站反代

目标内容是公开的 AI/科技新闻，正文以文字为主。这类内容用正文提取（Readability / trafilatura / Reader API） 的命中率远高于全站反向代理：页面更干净、加载更快、被反爬拦截率更低、带宽消耗小一个数量级。 全站反代（连 JS/CSS/图片一起中转）是最重、最脆、最贵的路径，只在确实需要原文完整排版时才考虑。

二、五个底层逻辑不同的方案

#方案底层逻辑成本上线工作量主要风险
P1 现成阅读器 API（r.jina.ai） 零自建：链接改写成第三方 Reader API URL，内容由它代取 免费档 ≈30 分钟（改 1 处链接改写） 大陆可达性需实测；第三方依赖与限额
P2 Cloudflare Worker 自建阅读器 免费 serverless 上跑「抓取 + 正文提取」，点击时实时出阅读页 免费额度内 1–2 天（Worker + Readability 移植） workers.dev 大陆稳定性；反爬强的站点失败
P3 构建期全文快照（扩展现有管线） GitHub Actions 每 2h 抓取时顺带存正文，点击时读自家静态快照 0 边际成本 2–4 天（管线 + reader 页 + data 结构） 快照覆盖仅限数据集内条目；存储/抓取时长膨胀

我的判断与推荐路线

2026-07-19 更新：P1 经实测已弃用。r.jina.ai 对 Techmeme 等站返回 Cloudflare 403/验证码拦截页， 部分页面内容为链接残渣，体验不达标。全线采用 P3 快照模式：快照条目走扩展内阅读页， 无快照条目直接打开原始链接（依赖用户自身网络）。

不要一步到位，分两步走：

  1. 今天：P1（r.jina.ai）先上线验证。改动只有 NewsCard 一处链接改写，30 分钟。立刻回答两个关键未知数：① r.jina.ai 在大陆的实际可达性与速度；② 目标源的正文提取命中率。这两个答案决定后面选哪条重型路线。
  2. 本周：P3（管线快照）作为主力方案落地。它与你的架构天然同构——你已经有一条每 2 小时抓 100+ 源的管线和一个静态托管，把「正文提取」加进去，边际成本为零，可控性最强，还能顺带获得「源站挂掉也能读」的离线能力。P2/P5 留作 P1 验证失败（jina 不可达）且 P3 未就绪时的过渡；P4 仅当确实需要原站完整排版时再考虑。

合规与可持续注意：只中继公开报道正文；不破解付费墙；中继必须做「数据集 URL 允许列表」防止被当公开代理；控制抓取频率尊重源站。
