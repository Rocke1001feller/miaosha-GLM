方案 B4（推荐主线）

构建期 LLM 精翻：把双语做进快照契约

底层逻辑：与 P3 完全同构——快照步骤里，对 content_html 的文本节点逐段调 LLM（GLM-4.5-Flash / DeepSeek 等），产出结构完全一致的 content_html_zh，与英文快照一起进 data 分支与 Pages。用户打开即是双语，质量是五个方案里最好的。

工作方式

snapshot 步骤（已有）产出 content_html → 新增 translate 步骤： 遍历 DOM 文本节点（跳过 pre/code）→ 按段落批量调 LLM 同构替换 → content_html_zh（标签结构 1:1 保留） 缓存 paragraph 哈希，重复内容不重复翻 → 快照 JSON: { content_html, content_html_zh, translated: bool } → reader 页：并行渲染英块 + 中块（灰显），三态切换

成本

≈0 到极低
  • GLM-4.5-Flash 有免费档（够每天 2 次 × 443 篇的规模）；DeepSeek 约几元/百万 token，月成本个位数人民币。
  • LLM 并发与上下文大，443 篇全文翻完通常几分钟，比 B1 的免费端点快且稳。
  • key 放 GitHub secrets，管线自主可控。

优点

  • 质量天花板：LLM 懂上下文、能遵守术语表（agent=智能体、vibe coding 保留、产品名不翻）、能跳过代码块；
  • 用户打开即双语：零客户端成本、零网络依赖、对所有人一致；
  • 与 P3 架构同构：失败有快照、增量有缓存、问题可留档复跑；
  • 后续可平滑加「AI 摘要（真摘要，非截取）」——同一个 LLM 步骤顺带产出。

局限与风险

  • 需要申请并管理一个 LLM API key（一次性工作）；
  • LLM 偶尔会漏段或改写结构——需要校验（段落数对比，不一致则该段保留英文）；
  • 快照体积约翻倍（可接受，data 分支单提交上限还远）。

落地步骤

  • ① bigmodel 开放平台拿 GLM-4.5-Flash key → GitHub secrets 加 LLM_API_KEY；
  • ② ai-news 加 src/translate/llm.ts（批量段落、术语表、结构校验、缓存）；
  • ③ snapshot 步骤挂接 translate；快照 JSON 加 content_html_zh/translated；
  • ④ reader 页双语渲染 + 三态切换；扩展类型契约同步；
  • ⑤ 跑一轮看质量与失败段，再全量放开。
