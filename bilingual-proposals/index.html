快照之后：让英文新闻「英下显中」

现状：P3 快照模式让大陆用户能读到原文（成功率 69%），但其中大量文章是纯英文，很多用户无法顺畅阅读。 目标：阅读页支持双语——英文段落下方显示对应中文翻译。要求：成本低、体验快、可维护。

一、问题的骨架：三条决策轴

轴 1：翻译的时机 —— 构建期 vs 阅读时

构建期翻译（管线里翻好存进快照）：用户打开即是双语，零等待、零客户端成本、对所有人一致； 代价是每次运行要为全部 443 篇付费/耗时。这与你选 P3 的哲学同源——把运行时问题变成构建时问题。 阅读时翻译（用户点开才翻）：只为真正被阅读的内容付出，但大陆用户调境外翻译 API 天然不稳，且每人都付一次延迟。

轴 2：翻译的算力位置 —— Actions / 第三方云 / 用户设备

GitHub Actions（境外干净 IP，调 Google 翻译免费端点已被标题翻译验证可行）；第三方翻译云（DeepL/GLM/DeepSeek，要 key、要钱或限量）； 用户设备（Chrome 138+ 内置 Gemini Nano，离线免费但机型/版本有门槛）。算力位置决定了谁能用、稳不稳、花不花钱。

轴 3：中英如何对齐 —— 这是排版问题不是翻译问题

「英文下面显示中文」要求段落级对齐。两种实现：同构 DOM 双份（快照存 content_html 与 content_html_zh，结构一致，阅读页并行遍历块级元素逐块对照渲染）； 段落对数组（快照存 [{en, zh}]，牺牲标题/列表等结构）。前者保真度高、实现也不复杂，是推荐契约。 交互上必须给三态切换：双语 / 仅中文 / 仅英文——双语是默认，但不是所有人都想要双倍长度。

二、五个底层逻辑不同的方案

#方案底层逻辑成本质量主要风险
B1 构建期批量预翻译（Google 免费端点） 扩展现有标题翻译机制到全文段落，运行时零成本 免费 机翻，中等 443 篇/次的量可能触发限流；运行时长膨胀
B2 阅读时滚动懒翻译（公共端点） 只翻被读到的段落，滚动到哪翻到哪 免费 机翻，中等 大陆调境外翻译端点不稳；首段就有延迟
B3 端侧模型翻译（Chrome 内置 AI） 翻译算力在用户设备上，离线、免费、隐私 免费 小模型，中等偏上 Chrome 版本/机型门槛；首次需下载模型
B4 构建期 LLM 精翻（自有 API key） 管线用 GLM/DeepSeek 等 LLM 产出同构双语 DOM ≈0 到极低 最好 需管理 key 与成本；prompt 需保结构
B5 渐进揭示式多源路由 不是翻译源，是编排框架：多源择优 + 按需揭示 视路由 取决于源 复杂度最高；需要前两期沉淀后再做

最终实施建议

  1. 主线：B4（构建期 LLM 精翻）。与 P3 同构——快照步骤里对 content_html 的文本节点逐段调 LLM（GLM-4.5-Flash 免费档起步，key 放 GitHub secrets），产出同构 content_html_zh 进快照契约；reader 页并行渲染「英段 + 灰显中段」，顶栏三态切换（双语/仅中/仅英）。所有用户打开即双语，不依赖其浏览器与网络。
  2. 兜底：B3（端侧 Nano）二期再做。对没有译文的条目（快照失败、7d 旧文）提供「在本地翻译」按钮——有 Nano 用 Nano，没有则隐藏。不动数据契约，纯增量。
  3. 不选 B1/B2 的原因：B1 全量机翻的运行时长与限流风险高且质量一般；B2 依赖大陆用户直连境外翻译端点，恰好在最需要翻译的人群身上最不稳。
  4. B5 暂缓：多源路由是 B4+B3 都上线后的自然演化，不值得现在付复杂度。

质量增强建议（B4 内建）：prompt 里附 AI 新闻术语表（agent=智能体、vibe coding 保留原文等），并要求跳过 <pre>/<code> 内文本。
