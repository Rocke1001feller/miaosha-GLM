方案 P4

日本服务器全透明反向代理

底层逻辑：整站中转——你的日本服务器对任意目标 URL 做完整反向代理（HTML/CSS/JS/图片全部改写转发），用户看到的就是原站本身。保真度天花板，但也是五个方案中最重、最脆、最危险（滥用面）的一个。

点击时序

用户在 popup 点击新闻卡片 → 改写为 https://<jp-relay>/p/<base64url 原文> → 服务器拉取原站 HTML，重写其中所有相对/绝对资源链接（CSS/JS/图/字体）指向自己 → 后续所有子资源请求都经服务器中转 → 用户看到「原站原样」页面（包括它的广告、弹窗与反爬验证）

组成

  • 反代实现：Caddy / nginx + 链接重写模块，或 ~200 行 Go/Node 自写（fetch + HTML 流式改写 + Set-Cookie/CSP 头处理）。
  • 弹窗内跳转链接同样需改写（否则用户点进文章内链接就掉出代理）。
  • WebSocket / Service Worker / 重定向链 / 验证码页的边角处理（真正的复杂度在这里）。

成本

服务器已有 0 新增
  • 服务器现成；但带宽是真成本：整页（含图/JS）单篇 1–5MB 经你中转，量上来后流量费/带宽峰值要考虑。

优点

  • 排版 100% 保真，任何站点形态都「看起来对」；
  • 不依赖正文提取算法的命中率。

局限与风险（务必读完再选）

  • 滥用风险最高：一个能代理任意 URL 的端点一旦被发现，就会被当免费公开代理刷爆。必须做硬限制：仅允许出现在当前新闻数据集中的 URL（动态允许列表），或带 HMAC 签名的一次性链接，否则不要上线。
  • 脆：Cloudflare 盾/验证码/JS 挑战页会把用户卡在反爬页（体验比打不开更差）；CORS、cookie SameSite、CSP 头处理坑多。
  • 重：带宽、并发、运维（证书续期、宕机监控）全是你的。
  • 合规面更宽：整站镜像式中转 vs 阅读器式正文引用，前者更接近"复制站点"。

什么时候才选它

  • 只有当你确认「必须给用户看原站完整排版与交互」（如交互式图表、原站评论）时才值得。对"读 AI 新闻"这个需求，P2/P3 的阅读版式几乎总是更好的体验。
